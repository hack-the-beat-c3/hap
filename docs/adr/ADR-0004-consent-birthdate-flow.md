# ADR-0004: 팀원 2 개인정보 동의·생년월일 입력 플로우
- Status: Proposed
- Date: 2026-08-29
- Owners: DRI 배정 대기(AGENTS.md §1, 팀 R&R 미정), Reviewer 배정 대기(사람 승인 대기)
- Related: PRM_TEAM2.md Goal 1, ADR-0001, AGENTS.md §2.2/§3/§6

## Context

파티 참가자가 사주·오행 개인화를 이용하려면 원본 생년월일과 출생시각을 브라우저에 입력해야 한다. 이 값은 계산에 필요하지만 서버, 로그 또는 영속 저장소로 보내지 않는다는 ADR-0001과 AGENTS.md §2.2의 경계를 입력 화면에서도 유지해야 한다. 사용자는 처리 목적과 거부 시 영향을 입력 전에 이해하고, 제출 전에 값을 확인·수정할 수 있어야 한다.

현재 저장소의 승인된 계산 계약은 `src/saju/engine.ts`의 `SajuInput`, `SajuResult`, `SajuCalcResult`, `calculateSaju`와 `src/kstToday.ts`의 `getTodayInKST`이다. `SajuInput`에는 닉네임이 없으므로 화면의 로컬 폼 모델은 닉네임과 계산 입력을 구분해야 한다. 실제 서버와 결과 공유 이미지 생성 기능은 아직 없다. 또한 다른 두 팀원 브랜치가 `src/App.tsx`와 `src/App.css`를 수정 중이므로, 이 ADR은 통합 진입점을 변경하지 않는 독립 플로우의 경계만 정한다.

이 ADR의 동의 문구는 팀 검토 전 임시 문안이다. 등록된 개인정보 처리방침이나 법률 검토를 대신하지 않으며 법률 준수를 보장하지 않는다.

## Decision

1. **화면 순서와 이동:** `안내·동의 → 입력 → 확인 → 제출 완료`의 네 단계로 구성한다. 필수 동의 전에는 입력 단계로 갈 수 없다. 입력 단계에서는 동의 단계로 뒤로 갈 수 있고 입력값은 즉시 폐기한다. 확인 단계에서는 `수정`으로 입력 단계에 돌아갈 수 있으며 이때만 메모리의 입력값을 보존한다. 제출 완료 뒤에는 민감 입력이 정리되므로 이전 단계로 돌아갈 수 없고, 새 입력을 시작해야 한다. 브라우저 뒤로가기는 앱 단계 이동으로 처리하되 완료 상태에서 민감 값을 복원하지 않는다.

2. **입력 필드와 필수 여부:** 화면의 로컬 모델은 `nickname: string`과 `sajuInput: SajuInput`으로 분리한다. 닉네임은 필수다. `SajuInput`과 정확히 맞물리는 필수 값은 `calendarType: 'solar' | 'lunar'`, `year: number`, `month: number`, `day: number`, `birthTime: { hour: number; minute: number } | 'unknown'`이다. 출생시각은 시·분 입력과 `'unknown'` 선택 중 하나가 필수이며, `'unknown'`이면 시간주를 제외한 간이 해석임을 표시한다. `isLeapMonth?: boolean`은 음력일 때만 노출하며 윤달 선택 여부를 담고, 양력에서는 생략한다. 닉네임은 `SajuInput`에 억지로 추가하지 않는다.

3. **동의 항목:** 두 항목을 분리한다. 필수 `서비스 이용 필수 동의`의 임시 문안은 목적을 사주·오행 계산, 처리방식을 브라우저 메모리에서의 일시 처리와 계산 직후 폐기, 거부 영향을 핵심 입력·계산 플로우 이용 불가로 설명한다. 선택 `결과 공유 이미지 생성 동의`는 목적을 향후 공유 이미지 생성으로 설명하되 해당 기능은 현재 사용하지 않고 만들지 않으며, 동의 여부와 무관하게 핵심 플로우가 진행됨을 명시한다. 선택 동의를 거부해도 입력과 제출을 막지 않는다.

4. **동의 버전과 상태:** 코드 상수 `CONSENT_VERSION = 'consent-v1-2026-08-29'`로 문안 버전을 식별한다. 동의 상태는 `{ requiredAccepted: boolean; optionalShareImageAccepted: boolean; consentVersion: string; consentedAt: string }`까지만 현재 페이지의 메모리에 유지하며 원본 생년월일·시각을 포함하지 않는다. `consentedAt`은 필수 동의를 확정한 시각의 ISO 문자열이다. 새로고침, 취소 또는 완료 시 사라지고 서버나 영속 저장소에 저장하지 않는다.

5. **원본 입력의 메모리 수명:** 원본 `year`, `month`, `day`, `birthTime`, 달력·윤달 선택은 폼이 열린 동안 React state에만 둔다. 제출 성공 또는 취소 시 즉시 초기화한다. `localStorage`, `sessionStorage`, URL 및 query string, DOM `data-*` attribute, console, 분석 도구, 오류 보고서에 기록하지 않는다. 오류 객체나 메시지에도 원본 값을 보간하지 않는다.

6. **새로고침:** 민감 입력과 동의 상태를 자동 복원하지 않는다. 새로고침하면 안내·동의 단계부터 다시 시작한다. 영속 저장을 하지 않는 개인정보 최소화 원칙을 새로고침 편의보다 우선한다.

7. **계산 호출:** 확인 화면에서 `제출`을 누른 순간 브라우저 안에서 `calculateSaju(sajuInput, getTodayInKST())`를 직접 한 번 호출한다. 승인된 실제 계약을 사용하고 mock이나 별도 계산기를 만들지 않는다. `SajuCalcResult`가 실패이면 `SajuError.message`를 화면에 표시하고 완료로 전환하지 않는다. 성공이면 반환된 `SajuResult`에서 allowlist 필드만 골라 로컬 payload를 만든다.

8. **전송 allowlist와 현재 경계:** 향후 서버 경계 타입은 다음으로 고정한다.

   ```ts
   import type { FiveElement, SajuResult } from '../saju/engine'

   interface ParticipantDerivedPayload {
     nickname: string
     dominantElement: FiveElement
     elementBalance: Record<FiveElement, number>
     calculationVersion: SajuResult['calculationVersion']
   }
   ```

   `nickname`, `dominantElement`, `elementBalance`, `calculationVersion`만 포함한다. 원본 `calendarType`, `isLeapMonth`, `year`, `month`, `day`, `birthTime`과 결과의 `todaySummary`, `isSimplified`, `timeProvided`, 동의 상태·시각은 제외한다. 이 저장소에는 실제 서버가 없으므로 현재 `제출`은 네트워크 요청을 만들지 않고 이 allowlist 객체를 로컬에서 구성한 뒤 완료 상태로 전환하는 데서 끝난다. 이는 ADR-0001의 브라우저 계산 경계를 따른다.

9. **취소·수정·오류·중복 제출:** 취소는 어느 미완료 단계에서든 입력과 동의 상태를 지우고 안내·동의 단계로 돌아간다. 확인 화면의 수정은 입력값을 보존해 입력 단계로 돌아간다. 제출을 시작하면 버튼을 비활성화하고 idempotent guard로 같은 폼 세션의 payload 구성과 상태 전이를 한 번만 허용한다. 브라우저의 느슨한 날짜 보정을 신뢰하거나 입력 레이어에 별도 달력 검증을 새로 만들지 않는다. `calculateSaju`가 반환하는 `INVALID_DATE`, `IMPOSSIBLE_LEAP_MONTH`, `FUTURE_DATE`, `OUT_OF_RANGE`의 `SajuError.message`를 그대로 사용자에게 보여주고 입력 단계로 수정할 수 있게 한다.

10. **문구 근거와 승인·변경 책임:** 이 ADR의 동의 문구는 제품 설계를 위한 임시 문안이며 실제 서비스 배포 전에 팀의 지정 책임자와 운영진·법률 검토 담당자의 승인이 필요하다. 현재 R&R이 미정이므로 특정 승인자를 임의 지정하지 않는다. 승인 전에는 이 문구를 개인정보 보호법 준수 문안으로 표현하지 않는다. 문구, 목적, 항목 또는 보관 경계가 바뀌면 이 ADR에 변경 사유와 새 `CONSENT_VERSION`의 버전 이력을 추가하고 다시 사람 리뷰를 받는다.

11. **구현·통합 경계:** 후속 구현은 `src/App.tsx`를 건드리지 않고 `src/consent/` 같은 독립 모듈에 둔다. `src/saju/SajuForm.tsx`를 호출하거나 수정하는 방식도 채택하지 않는다. 다른 두 팀원 브랜치가 이미 `src/App.tsx`와 `src/App.css`를 수정 중이므로 실제 화면 합성, 라우팅 및 스타일 조합은 충돌을 검토한 팀 차원의 후속 결정과 별도 변경으로 남긴다.

## Alternatives

- **동의와 입력을 한 화면에 배치:** 단계 수는 줄지만 처리 안내를 읽고 선택한 뒤 민감 값을 입력한다는 경계와 제출 전 확인이 흐려져 기각한다.
- **입력값을 브라우저 저장소에 임시 보관:** 새로고침 복원은 편리하지만 원본 생년월일·시각의 수명을 늘리고 ADR-0001의 메모리 전용 경계를 약화하므로 기각한다.
- **서버에서 계산하거나 원본을 전송:** 클라이언트 구현은 단순해질 수 있으나 원본 개인정보 비전송 결정과 충돌하므로 기각한다.
- **별도 날짜 검증기 또는 계산 mock 작성:** 기존 `calculateSaju`와 검증 규칙이 어긋날 수 있으므로 기각하고 승인된 함수의 판별 결과를 사용한다.
- **현재 `App.tsx`에서 바로 조합:** 세 브랜치 간 병합 충돌과 이 작업의 권한 밖 통합 결정을 만들므로 기각한다.

## Consequences

- 사용자는 처리 안내에 필수 동의한 뒤 입력하고, 제출 전에 값을 확인·수정할 수 있다. 선택 동의는 핵심 플로우에 영향을 주지 않는다.
- 원본 생년월일·시각과 동의 상태는 페이지 메모리를 벗어나지 않으며 새로고침 편의와 완료 후 뒤로가기를 포기한다.
- 서버가 생기기 전까지 제출 완료는 로컬 allowlist 객체 구성만 뜻한다. 네트워크 전송 완료나 개인정보 처리방침 등록을 주장할 수 없다.
- 선택 공유 항목은 현재 사용하지 않으므로 이미지를 만들거나 해당 동의를 기능 구현 근거로 삼지 않는다.
- 독립 모듈 구현은 병렬 브랜치 충돌을 줄이지만 실제 앱 노출은 팀이 정할 후속 통합 작업 전에는 이뤄지지 않는다.
- 임시 동의 문안은 법률·운영 검토 결과에 따라 바뀔 수 있으며, 변경 때 버전 이력과 테스트 기대값도 함께 개정해야 한다.

## Verification / Rollback

후속 구현에서는 아래 제품 정책을 컴포넌트 테스트로 검증하고, 브라우저 개발자 도구로 저장소·URL·console·네트워크에 원본 입력이 남지 않는지 확인한다.

검증에서 원본 입력의 영속 저장·전송, 중복 payload, 선택 동의에 따른 진행 차단 또는 계산 계약과 다른 날짜 판별이 발견되면 플로우 출시와 앱 통합을 중단한다. 독립 모듈 변경을 되돌리고 계산 엔진은 건드리지 않는다. 수정안은 이 ADR의 개인정보 경계와 실제 `SajuInput`/`SajuResult` 계약을 다시 대조하고 사람 리뷰를 받은 뒤 별도 변경으로 재구현한다.
